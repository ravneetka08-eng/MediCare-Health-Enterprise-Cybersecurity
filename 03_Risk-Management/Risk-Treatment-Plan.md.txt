# 1. Purpose

This document defines how cybersecurity risks requiring treatment are
converted into accountable, measurable and verifiable remediation
activities.

A risk treatment is not considered complete simply because:

- a recommendation was made;
- a ticket was created;
- software was installed;
- a configuration was changed;
- an action owner reports completion.

Treatment completion requires appropriate implementation evidence and,
where practical, validation that the treatment has reduced the
identified risk.

# 3. Treatment Principles

Risk treatments should be:

## Specific

The action must state exactly what will change.

## Measurable

Completion should be capable of verification.

## Accountable

A named role must own the action.

## Risk-Based

Priority should reflect risk rather than convenience alone.

## Time-Bound

Material actions should have target completion dates.

## Evidence-Based

Completion claims should be supported by evidence.

## Operationally Safe

Treatment must consider business and clinical consequences.

Each material treatment action should include:

| Field | Purpose |
|---|---|
| Action ID | Unique treatment identifier |
| Risk ID | Risk being treated |
| Control ID | Security control being implemented/improved |
| Action Description | Exact remediation required |
| Action Owner | Team responsible for implementation |
| Risk Owner | Accountable business/technology owner |
| Priority | Treatment urgency |
| Target Date | Expected completion |
| Dependencies | Prerequisites or constraints |
| Change Requirement | Whether formal change control is required |
| Implementation Status | Current state |
| Evidence Required | Proof of implementation |
| Validation Method | How effectiveness will be tested |
| Result | Validation outcome |
| Residual Risk Effect | Expected/actual risk reduction |
| Closure Approval | Authorised closure decision |

# 5. Treatment Status

Treatment actions may be:

- Proposed
- Approved
- Scheduled
- In Progress
- Blocked
- Implemented — Pending Validation
- Validation Failed
- Remediation Required
- Validated
- Closed
- Cancelled / Superseded

"Implemented" and "Validated" are deliberately separate states.

---

# 6. Priority

## Critical

Urgent treatment required.

May require:

- immediate containment;
- executive visibility;
- emergency change;
- accelerated remediation.

## High

Priority remediation required within the agreed treatment timeframe.

## Medium

Planned remediation within normal risk-management cycles.

## Low

Managed through routine improvement.

Priority does not automatically determine implementation timing.

Clinical safety, service availability and change risk must also be
considered.

# 8. Failed Treatment

A treatment must not be closed if validation demonstrates that the
control remains ineffective.

Example:

Action:

Remove local administrator access from Reception users.

Implementation team reports:

Complete.

Security validation finds:

reception.user remains a member of a group indirectly granting local
administrator privileges.

Result:

Validation Failed.

Required response:

- reopen treatment;
- investigate permission inheritance;
- correct configuration;
- retest;
- retain evidence.

---

# 9. Treatment Dependencies

Cybersecurity remediation may depend on:

- vendor support;
- application compatibility;
- procurement;
- maintenance windows;
- business approval;
- clinical scheduling;
- architecture changes;
- licensing;
- staff availability;
- cloud-service capability.

Dependencies should be documented rather than allowing treatment
deadlines to fail without explanation.

---

# 10. Overdue Treatment

Where a treatment action becomes overdue:

1. Action Owner provides status and reason.
2. Cybersecurity assesses change in exposure.
3. Risk Owner is informed.
4. Revised target date requires justification.
5. Additional compensating controls are considered.
6. Material delays are escalated.
7. Risk rating is reassessed where appropriate.

Repeatedly changing a target date without risk review is not an
acceptable substitute for treatment.

---

# 11. Treatment Validation

Validation methods may include:

- configuration inspection;
- command output;
- authentication testing;
- positive access testing;
- negative access testing;
- vulnerability rescanning;
- SIEM event validation;
- log review;
- recovery testing;
- firewall testing;
- cloud configuration review;
- evidence inspection.

Validation should answer:

"Did the treatment actually reduce the risk in the way we expected?"
