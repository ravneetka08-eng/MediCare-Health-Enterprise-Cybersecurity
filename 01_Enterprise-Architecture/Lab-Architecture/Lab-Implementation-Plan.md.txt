# 1. Purpose

This document defines the technical laboratory used to implement,
test and demonstrate representative cybersecurity controls for the
fictional healthcare enterprise.

The laboratory is not intended to reproduce the scale of a real
healthcare organisation.

Instead, it provides representative systems through which enterprise
security architecture, controls, testing, monitoring, incident
response and assurance activities can be practically demonstrated.

# 5. Scope Boundary

## In Scope

Only systems owned and controlled within the project laboratory.

This includes:

- project virtual machines;
- project-created AWS resources;
- synthetic data;
- project network segments;
- authorised security testing.

## Out of Scope

The following are prohibited:

- real healthcare systems;
- real hospital infrastructure;
- real patient information;
- unauthorised systems;
- public vulnerability scanning without permission;
- real credential harvesting;
- disruptive testing against third parties;
- exploitation of real medical devices.

# 7. Production-vs-Lab Limitation

A real healthcare enterprise would normally contain substantially
greater scale and complexity, including:

- multiple domain controllers;
- high availability;
- multiple sites;
- enterprise firewalls;
- dedicated network infrastructure;
- large endpoint fleets;
- enterprise EDR;
- enterprise SIEM infrastructure;
- privileged-access platforms;
- redundant infrastructure;
- formal backup platforms;
- production clinical applications;
- medical devices;
- vendor-managed systems;
- dedicated SOC capability.

These are represented conceptually where implementing them at real
scale is impractical for a student-controlled laboratory.

The project must clearly distinguish between:

1. technically implemented controls;
2. simulated controls;
3. architecture-only controls.

# 9. Cost Principle

The project should use free, open-source, trial, educational or
student-access technologies where practical.

AWS resources must remain within the user's available educational
account limits wherever possible.

Resources that may incur charges must not be created without
understanding the associated cost implications.

---

# 10. Safety Principle

The environment is a defensive cybersecurity learning laboratory.

Deliberately vulnerable configurations must:

- remain isolated where practical;
- contain no real sensitive information;
- be created only when required for an authorised test;
- be restored or remediated following testing.

Virtual-machine snapshots should be taken before significant
configuration changes or controlled failure scenarios.
