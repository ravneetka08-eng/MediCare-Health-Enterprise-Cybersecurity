# 1. Purpose

This document defines the technical laboratory used to implement,
test, validate and demonstrate representative cybersecurity controls
for a fictional healthcare enterprise.

The laboratory does not attempt to reproduce the physical scale,
availability or infrastructure capacity of a real healthcare
organisation.

Instead, it implements selected enterprise security patterns within
a controlled student environment.

The project follows the model:

# 2. Lab Design Philosophy

The project separates:

1. enterprise architecture;
2. laboratory implementation;
3. simulated components.

This distinction prevents the reduced-scale laboratory from being
misrepresented as a production healthcare environment.

The model is:

REALISTIC ENTERPRISE ARCHITECTURE
              |
              v
SELECTED SECURITY CAPABILITIES
              |
              v
REDUCED-SCALE LABORATORY
              |
              v
REAL TECHNICAL CONFIGURATION
              |
              v
REAL CONTROL TESTING
              |
              v
LAB-GENERATED EVIDENCE
              |
              v
ENTERPRISE RISK AND CONTROL ANALYSIS

The enterprise architecture represents organisational requirements
and security patterns.

The laboratory provides practical implementation and validation of
selected controls.

# 4. Resource Constraint

The primary laboratory constraint is physical memory.

The host contains 16 GB RAM.

Running every planned virtual machine simultaneously would create
unnecessary resource contention and may reduce host and guest
performance.

The laboratory will therefore use:

## Staged VM Operation

Only systems required for the active technical scenario will normally
be powered on.

Example IAM scenario:

DC01            ON
WIN-REC01       ON
WIN-CLIN01      ON when required
SEC-MON01       OFF
VULN01          OFF

Example detection scenario:

DC01            ON
WIN-REC01       ON
SEC-MON01       ON
WIN-CLIN01      OFF when unnecessary
VULN01          OFF

Example vulnerability-management scenario:

VULN01          ON
Target VM       ON
DC01            ON only where required
SEC-MON01       OFF where unnecessary
Other clients   OFF

This is a laboratory capacity-management decision.

It must not be interpreted as an enterprise healthcare availability
or infrastructure design.

# 7. Technology Selection

## Virtualisation

Selected:

Oracle VirtualBox

Reason:

- already available on the host;
- compatible with the Windows 11 Home environment;
- supports Windows and Linux guests;
- supports snapshots;
- provides suitable virtual networking;
- sufficient for the project's representative laboratory.

The use of VirtualBox is a laboratory implementation choice.

The architecture and administration concepts remain transferable to
enterprise virtualisation platforms.

# 10. Scope Boundary

## In Scope

Only systems owned or authorised for the project.

This includes:

- local project virtual machines;
- project virtual networks;
- project-created AWS resources;
- synthetic information;
- project security tools;
- authorised security testing.

## Out of Scope

The following are prohibited:

- real hospital systems;
- real healthcare infrastructure;
- real patient information;
- unauthorised third-party systems;
- unauthorised public scanning;
- real credential harvesting;
- disruptive testing against external systems;
- exploitation of real medical devices.

---

# 11. Data Requirements

The laboratory will use synthetic information only.

Synthetic patient information may include:

- fictional patient identifier;
- fictional name;
- fictional date of birth;
- fictional appointment;
- fictional clinical information;
- fictional contact details.

No real patient or healthcare information is required.

---

# 12. Snapshot Strategy

Snapshots will be used at important technical milestones.

Representative snapshot points include:

- clean operating-system installation;
- pre-Active Directory configuration;
- post-domain-controller configuration;
- pre-hardening;
- pre-security-test;
- pre-controlled misconfiguration;
- pre-incident exercise.

Snapshots support:

- recovery;
- experimentation;
- repeatable testing;
- rollback following configuration failure.

Snapshots are not treated as enterprise backups.

# 15. Cost Management

The project prioritises:

- free tools;
- open-source technologies;
- educational licensing;
- student access;
- AWS educational resources.

Before creating AWS resources, the project will consider:

- whether the resource incurs cost;
- whether a free/educational option exists;
- whether the resource needs to remain running;
- whether it can be deleted after testing.

Unused cloud resources should be removed when no longer required.

---

# 16. Safety Principle

The laboratory is intended for defensive cybersecurity learning.

Deliberately weakened configurations must:

- remain within authorised systems;
- contain no real sensitive data;
- be introduced only where required;
- be documented;
- be remediated or rolled back after testing.

Systems intentionally placed into a vulnerable state should not be
directly exposed to the public Internet.

---

# 17. Production-vs-Lab Limitation

A real healthcare enterprise may contain:

- multiple data centres;
- multiple domain controllers;
- high availability;
- redundant DNS;
- multiple geographic sites;
- enterprise firewalls;
- network-access control;
- large endpoint fleets;
- enterprise EDR;
- dedicated SIEM infrastructure;
- privileged-access management platforms;
- identity governance;
- enterprise vulnerability-management platforms;
- enterprise backup infrastructure;
- production clinical applications;
- medical devices;
- vendor-managed technology;
- dedicated security operations personnel.

The laboratory implements selected representative security patterns.

The project therefore distinguishes:

IMPLEMENTED

A control or technology actually configured and tested.

SIMULATED

A process or scenario represented safely without implementing the
full production technology.

DESIGN ONLY

An enterprise capability represented in architecture but not
technically implemented.

This distinction must be maintained throughout project reporting.
